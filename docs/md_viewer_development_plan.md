# MDビューアアプリ 開発計画

## 1. 目的

翻訳・研究用に作成したMarkdownファイル(FREUD_訳語集、freud_lacan_delta_comparison、各種翻訳原稿など)を、Kindleのような読書体験で閲覧するためのWebアプリを作る。実装はClaude Codeを使用。

## 2. 対象環境

- **Primary**: Chromebook(ChromeOS / Chrome ブラウザ)
- **Secondary**: スマートフォン(Android / iOS ブラウザ)

## 3. 決定事項サマリー

| 項目 | 決定内容 |
|---|---|
| しおり・既読位置の保存 | localStorage(即時反映のキャッシュ)+ JSONエクスポート/インポート(バックアップ・端末間移動) |
| ファイルの扱い方 | Chromebookはフォルダ丸ごと参照、スマホは個別ファイルをインポート |
| 実行環境(MVP) | シンプルな単一HTMLアプリ(PWA化・GitHub Pagesホストは Phase 2以降) |

## 4. MVPスコープ

### 4.1 ファイル読み込み

- **Chromebook**: File System Access API(`showDirectoryPicker`)でフォルダを指定 → 内包する `.md` を自動スキャンして一覧(本棚)表示。ディスク上の実ファイルを直接参照するため、Claude Codeでの編集がそのまま反映される。
- **スマホ**: `<input type="file" multiple accept=".md">` で個別ファイルを選択 → 本文をIndexedDBにインポート(コピー保存)。File System Access APIの`showDirectoryPicker`はAndroid/iOSブラウザ非対応のため、この方式で代替する。
- 両者とも「ファイル一覧(本棚)画面」からファイルを選んでビューアを開く、という同じUI/UXにする。

### 4.2 しおり・既読位置

- 1ファイルにつき複数しおりを設定可能。任意のメモを添付できる。
- スクロール位置(既読位置)を自動保存し、次回開いた時に続きから表示。
- 保存先はlocalStorage。加えて「しおり・既読位置・アプリ設定」をまとめてJSONにエクスポート/インポートできる機能を用意し、バックアップおよび端末間の手動同期に使う。

### 4.3 ファイル内検索

- 現在開いているMD内でのテキスト検索。
- ヒット数表示、前後移動ボタン、該当箇所のハイライト。

### 4.4 フォント拡大縮小

- +/−ボタンまたはスライダーでフォントサイズを調整。
- 設定はlocalStorageに保存し、次回起動時も引き継ぐ。

### 4.5 選択部分をウェブで検索

- テキスト選択時にフローティングボタンを表示 → クリックで新規タブにWeb検索(Google等)を開く。

## 5. Phase 2以降(MVP後の拡張候補)

- **目次(TOC)自動生成**(実装済み): 見出し(#, ##, ###)からアウトラインを抽出し、クリックでジャンプ。
- **テーマ切り替え**: ライト/ダーク/セピア(Kindle風)。
- **PWA化 + GitHub Pagesホスティング**(GitHub Pagesホストは実装済み。PWA化は未着手 → §9.6): ホーム画面に追加してオフライン動作。アプリコードのみを公開リポジトリに置き、翻訳原稿本体は含めない(過去のPAT露出の経緯を踏まえ、公開範囲には要注意)。
- **Google Drive連携**(Drive上の.mdを参照する部分のみ実装済み。しおり同期は未実装 → §9.5): 家計簿アプリで実装済みのOAuth 2.0 + Drive JSONバックエンドの仕組みを流用し、しおり・既読位置を端末間で自動同期。
- **用語集連携**: 既存のLacan/Freud用語集(200語)と連動し、選択した語句が用語集に存在すれば定義をポップアップ表示する辞書機能。翻訳ワークフローとの直接連携になるため、実装難易度は高いが価値も大きい。

## 6. 技術構成案

- 単一HTMLファイル(`index.html`)+ 素のJavaScript(フレームワーク不要。既存のマインドマップアプリと同方針)
- Markdownレンダリング: `marked.js` 等の軽量ライブラリ(CDNまたはオフライン同梱)
- ファイルアクセス: File System Access API(Chromebook)/ File API(スマホ)
- データ永続化: localStorage(設定・しおりキャッシュ)+ IndexedDB(スマホ側のファイル本文コピー)

## 7. Claude Codeでの実装ステップ案

1. 基本UI(本棚一覧画面 + ビューア画面)の骨格を作成
2. Chromebook向けフォルダ読み込み(File System Access API)を実装
3. Markdownレンダリング + フォントサイズ調整機能
4. しおり機能(追加・一覧・ジャンプ)+ localStorage永続化
5. ファイル内検索機能
6. 選択テキストのWeb検索ボタン
7. スマホ向けファイルインポート(IndexedDB)機能
8. JSONエクスポート/インポート(しおり・設定のバックアップ)機能
9. 動作確認・微調整

## 8. 未決定事項(実装中に判断)

- 見開き/ページめくり型か、連続スクロール型か(Kindleは前者だが、Web実装コストは後者の方が低い)
- Markdownの見出しレベルごとの表示スタイル(既存の翻訳MDファイルのフォーマットに合わせて調整が必要になる可能性あり)

## 9. Phase 3 ロードマップ

### 9.0 背景

2026-08-16のレビューで、Chromebookから「Drive」を開くと「Google認証中...」で固まる不具合を修正した(P0-1)。直接原因は`file://`で開いていたこと(GoogleのOAuthは`https://`か`localhost`のオリジンしか受け付けない)、固まっていた原因はGISの`error_callback`未設定でPromiseが未解決のままだったこと。事前判定・`error_callback`・タイムアウト・401自動リトライを実装して解消済み。

この過程で、コードには現れない**構造的な課題**が3点判明した。以下のロードマップはこれらへの対応が骨格になっている。

1. **位置がピクセル依存** — 既読位置もしおりも`viewerContent.scrollTop`をそのまま保存しているため、フォントサイズを変えた瞬間・画面幅の違う端末に持っていった瞬間にズレる
2. **本の識別子が経路依存** — `relPath`をキーにしているが、同じファイルでもインポート(`名前.md`)・Drive(`フォルダ/名前.md`)・フォルダ読み込み(選んだ位置からの相対パス)で値が変わる。同じ本なのにキーが3種類になり、しおりが端末間で紐づかない
3. **バックアップが全上書き** — `importBackup()`が既存データを丸ごと置き換えるため、端末間同期に使うと相手側の変更を失う

**依存関係**: 9.1がボトルネック。9.4(ハイライト)も9.5(同期)も9.1の上に乗るため、機能追加より先に土台へ投資する方が結果的に早い。

### 9.1 P0-2 データモデル刷新 —— **実装済み(2026-08-16)**

実装の要点は `CLAUDE.md`「データモデル」節を参照。以下は当初の設計方針(そのまま実装された)。

- **`bookId`の導入**: ファイル名の正規化、または本文先頭のハッシュから安定したIDを生成する。ソース(`fs`/`idb`/`drive`)は「その本をどこから取得するか」という別レイヤーの情報として分離し、しおり・ハイライト・既読位置はすべて`bookId`をキーにする
- **位置を文字オフセットへ**: 本文プレーンテキスト先頭からの文字数で保存する。**既存の`getTextOffsetInViewer()`(`index.html`)がそのまま流用できる**
- **注釈モデルの統合**: しおり・ハイライト・メモを別機能にせず、1つの「注釈(annotation)」モデルにまとめる。ボタンもデータも増えすぎない

  ```
  { id, bookId, type: 'bookmark' | 'highlight',
    start, end,            // 本文プレーンテキスト上の文字オフセット
    quote,                 // 選択テキスト本体(再アンカー用)
    prefix, suffix,        // 前後20文字(本文編集でズレた時の復元用)
    color, note,
    createdAt, updatedAt, deleted }
  ```

- **マイグレーション**: 既存の`mdViewer.bookmarks`は`type:'bookmark'`として変換する。旧データは破棄せず残し、着手前にJSONエクスポートでバックアップを取っておく

### 9.2 P1-1 ハンドル永続化 + 「読書中」本棚 —— **実装済み(2026-08-16)**

実装の要点は `CLAUDE.md`「ハンドル永続化 + 「読書中」本棚」節を参照。以下は当初の設計方針(そのまま実装された)。

毎回フォルダ/ファイルを選び直す手間をなくす。鍵は**参照の永続化**で、ソースごとに手段が違う。

| ソース | 永続化方法 |
|---|---|
| フォルダ(fs) | `FileSystemDirectoryHandle`はstructured clone可 → IndexedDBに保存。起動時に`queryPermission({mode:'read'})`、必要ならワンクリックで`requestPermission()` |
| Drive | `folderId`/`fileId`をlocalStorageに保存し、トークン取得後に自動再取得 |
| インポート(idb) | 既に永続なのでそのまま |

本棚は「読書中(ピン留め)」「最近読んだ(`lastOpenedAt`順)」「すべて」の3セクションに分ける。ピン留め/解除ボタンと自動リストの併用が、手動管理の手間が最も少ない。

### 9.3 P1-2 モバイルUI再構成

機能ボタンが増えても本文スペースを圧迫しないようにする。ボタンを減らすのではなく、**UIを常時表示しない**のが正解。

- **本文タップでUIトグル**(Kindle方式) — 読書中はヘッダーもツールバーも非表示で本文100%。中央タップで表示/非表示
- **操作系を下端のボトムバーへ** — 目次・検索・注釈・文字サイズ・本棚。片手操作になるスマホでは上部ヘッダーより有利
- **パネルのオーバーレイ化** — 現状パネルは`flex: 0 0 auto`で本文を押し下げており、開くと本文表示領域が実際に縮む。**これがスマホで本文が狭くなる主因**(ボタンの数以上に)。半透明のボトムシートに変更し、スワイプで閉じる

9.4より先に着手すること。後からだとボタン配置を2回作り直すことになる。

### 9.4 P2-1 ハイライト + メモ

- **レイヤー再構築関数を1本作る**: 「素のHTML → 注釈ハイライト → 検索ハイライト」の順で毎回組み立て、そこを常に通す。現状`closeSearch()`が`renderedHTML`に戻すため、これをやらないと検索を閉じるたびに注釈が全部消える
- **再アンカー**: `start/end`で復元し、ズレていたら`quote` + `prefix/suffix`で近傍を再検索して自動修復する(W3C Web AnnotationのTextQuoteSelector相当)。**翻訳原稿は今後も編集されるため必須**
- 選択ツールバー(既存のWeb検索/文中検索の隣)にハイライトボタンを追加。色選択はハイライト後のポップオーバーで
- 注釈一覧パネル: ジャンプ・色フィルタ・メモ編集
- **注釈のMarkdown書き出し** — 引用+自分のメモの抜き書きが生成される。翻訳ワークフローに直結する

### 9.5 P2-2 Drive appDataFolder による自動同期

- スコープ`https://www.googleapis.com/auth/drive.appdata`を追加する。アプリ専用の隠しフォルダで、**原稿本体への書き込み権限は不要**(現状の`drive.readonly`に足すだけ)
- **同期単位は「本ごとに1ファイル」** — 全体を1ファイルにすると端末間の衝突が頻発する
- **マージ方式(全上書き禁止)** — 注釈`id`単位で`updatedAt`の新しい方を採用、削除はtombstone。これで「Chromebookでハイライト → スマホでメモ追加」が両方残る
- タイミング: 起動時と本を開く時にpull、変更時はdebounce(5〜10秒)でpush
- **前提**: 9.1の`bookId`統一。これなしでは同期しても端末間で紐づかない
- 既存のJSONエクスポート/インポートはオフライン用バックアップとして残す(ただしマージ方式に変更)

### 9.6 P3

- `marked.js`の自己ホスト + PWA化(オフライン読書)。現状CDN依存のためオフラインでは読めない
- `marked.parse()`の結果を無サニタイズで`innerHTML`に入れている点の見直し(自分の原稿だけなら実害は低いが、MD内の生HTMLは実行される)
- 注釈データのIndexedDBへの移行(localStorageの5MB上限対策)

### 9.7 作業ごとのモデルの使い分け

| 作業 | モデル | 理由 |
|---|---|---|
| 9.1 データモデル刷新 | Opus 5 | 既存データのマイグレーション設計が絡み、失敗するとしおりが消える |
| 9.3 モバイルUI再構成 | Opus 5 | CSSレイアウトの作り直し + 操作体系の設計。全体を見渡す必要がある |
| 9.5 同期のマージ設計 | Opus 5 | 競合解決ロジックはバグると気づきにくくデータが壊れる |
| 9.2 ハンドル永続化・本棚 | Sonnet 5 | パターンが確立した実装 |
| 9.4 ハイライト実装 | Sonnet 5 | 9.1が終わっていれば実装は素直 |
| 9.6 / 文言・CSS微調整 | Haiku 4.5 | 軽微な作業 |

9.1と9.3は、実装前にプランモードで設計を確定させてから着手する(§7の「変更は小さく刻む」方針にも合う)。
